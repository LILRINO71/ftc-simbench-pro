# Read the mates, then interpret the Java

FTC SimBench Pro should stop guessing mechanisms and **read them from the CAD assembly**. The main route is an extended one-click Onshape bookmarklet. It runs on the team's own signed-in assembly tab and pulls the assembly definition, mate features (limits and gear/rack relations), current mate values, per-Part-Studio tessellation with face colours, and material-based mass straight from Onshape's REST API. A STEP file is then no longer needed. OAuth is the wrong first step for two reasons. Onshape's API sends no CORS headers to third-party origins, so OAuth needs a server-side Worker anyway. And since October 2025 every private OAuth app or API key is held to **2,500 calls per user per year** on Free and EDU plans; the only exemptions are public App Store apps and browser client calls. For teams that don't use Onshape, which is probably the next-largest group with Fusion second (no FTC survey publishes numbers), the app should take two inputs. One is a **URDF zip**, the format nearly every CAD exporter already writes. The other is a small **"Export to SimBench" Fusion script**, with a SolidWorks macro next. Both should feed one **`ftc-sim-bench.robot` package**. Its joints are bound to the team's `hardwareMap` device names by **exact string**, the way Webots and ros2_control do it. Fuzzy matching only proposes those strings, and a device with no joint becomes a live gauge instead of a blocking question. For code, the answer is the path the repo has already started in an uncommitted `src/jvm.js`: a **generator-based Java-subset interpreter** with a JS mock of the FTC SDK. It runs FTCLib and Pedro Pathing from their real Java source, uses JS ports of Road Runner's Kotlin core, and runs every TeamCode file, including the team's own `MecanumDrive`, as written. CheerpJ's licence and wall-clock time make it the wrong runtime for this product.

## Onshape-first holds, though no one has counted FTC's CAD users

No source gives FTC CAD usage as numbers. Onshape claims, from unspecified "informal surveys", that it is "the most widely used CAD and PDM system among FIRST Robotics teams" and that "an overwhelming number of world championship teams used Onshape" ([Onshape blog](https://www.onshape.com/en/blog/first-robotics-cad-platform)). The vendor sponsorship landscape fits that order without proving it. **PTC (Onshape, Creo), Autodesk (Fusion, Inventor) and Dassault (SolidWorks) all give FTC teams free licences** ([FTC Docs: Software Sponsors](https://ftc-docs.firstinspires.org/en/latest/sponsors/software/software.html)). Community docs list Onshape, Fusion, SolidWorks and TinkerCAD, and call SolidWorks an "extreme learning curve" tool ([FTC Community Docs](https://www.firstcommunitydocs.com/cad/overview/)). FRC threads describe a continuing drift to Onshape ([Chief Delphi](https://www.chiefdelphi.com/t/solidworks-vs-onshape/495810)). General hobbyist surveys put Onshape near 1% ([CNCCookbook](https://www.cnccookbook.com/cnccookbook-2024-cad-survey-market-share-customer-satisfaction/)), which shows how different the FTC population is from the wider market and why those surveys can't stand in for it.

The working order is therefore **Onshape, then Fusion, then SolidWorks, then a long tail** (Inventor, FreeCAD, TinkerCAD). The app should log which import route each robot used, so the next version of this report can cite real numbers. Onshape also matters for a technical reason, not only a market one. It is the only FTC CAD tool whose joints can be read **from a browser with no install**, because the team's own session can call its API. Every other tool needs code running inside the desktop CAD program.

## Onshape's API already carries the whole robot: joints, colours and mass

Everything a simulator needs is in the REST API, in metres, and none of it requires STEP ([Onshape OpenAPI](https://cad.onshape.com/api/openapi)). The repo's bookmarklet in `src/onshapelink.js` fetches only the first two rows of the table below. It then matches Onshape occurrences to STEP parts by world transform, as `src/mates.js` describes, so teams still have to export and drop a STEP file. Adding the remaining rows removes the STEP step and supplies colour and mass directly.

| Need | Endpoint (prefix `/api/v{N}`) | Notes |
| --- | --- | --- |
| Tree, transforms, mates, connectors | `GET /assemblies/d/{did}/{wvm}/{wvmid}/e/{eid}?includeMateFeatures=true&includeMateConnectors=true&includeNonSolids=false&excludeSuppressed=true` | Occurrence transforms are row-major 4×4 and **absolute**. Each mate gives `matedEntities[2].matedCS` in the part frame. Joint world frame = `T_world_part × T_part_mate` ([Assemblies guide](https://onshape-public.github.io/docs/api-adv/assemblies/); [onshape-to-robot](https://github.com/Rhoban/onshape-to-robot/blob/master/onshape_to_robot/assembly.py)) |
| Limits and relations | `GET /assemblies/.../e/{eid}/features` | `limitsEnabled`, `limitAxialZMin/Max` (revolute), `limitZMin/Max` (slider). `BTMMateRelation` has `matesQuery`, `relationRatio`, `reverseDirection`. Values can be expressions or per-configuration ([onshape-to-robot](https://github.com/Rhoban/onshape-to-robot/blob/master/onshape_to_robot/assembly.py)) |
| Drawn pose | `GET /assemblies/d/{did}/{wv}/{wvid}/e/{eid}/matevalues` | `featureId`, `mateName`, current DOF values. Workspace or version only, not microversion ([OpenAPI](https://cad.onshape.com/api/openapi)) |
| Geometry and colour | `GET /partstudios/d/{did}/{wvm}/{wvmid}/e/{eid}/tessellatedfaces?outputFaceAppearances=true&chordTolerance=…&angleTolerance=…` | One call per unique Part Studio returns every part. The synchronous `/partstudios/.../gltf` is the alternative ([OpenAPI](https://cad.onshape.com/api/openapi)) |
| Mass, centroid, inertia | `GET /partstudios/d/{did}/{wvm}/{wvmid}/e/{eid}/massproperties` | One call returns a `bodies` map keyed by partId. Needs material density ([Part Studios guide](https://onshape-public.github.io/docs/api-adv/partstudios/)) |
| Part colour, name, material | `GET /metadata/d/{did}/{wvm}/{wvmid}/e/{eid}/p` | Bulk metadata for all parts. Colour is RGB 0–255 plus opacity ([robot_builder.py](https://github.com/Rhoban/onshape-to-robot/blob/master/onshape_to_robot/robot_builder.py)) |
| Configurations | `GET /elements/d/{did}/{wvm}/{wvmid}/e/{eid}/configuration` | Only needed when the assembly is configured. Pass `configuration=` on every later call ([OpenAPI](https://cad.onshape.com/api/openapi)) |

Most of the engineering is in fetching per Part Studio, not per part. Every instance in the definition carries `documentId`, `elementId`, `documentMicroversion`/`documentVersion`, `configuration` and `isStandardContent`. Grouping by that key collapses the eight identical goBILDA channels on a robot into **one tessellation call and one mass call**, placed eight times by occurrence transform. Linked vendor parts must be fetched at the vendor document's own version, with `linkDocumentId` set to the robot document. Otherwise access fails, and onshape-to-robot handles standard content exactly this way ([robot_builder.py](https://github.com/Rhoban/onshape-to-robot/blob/master/onshape_to_robot/robot_builder.py)). The call count then works out to about **five fixed calls plus two or three per unique Part Studio and configuration**. That estimate has not been measured on a real FTC assembly. Measuring it on the default robot's source document should be the first spike.

Two choices are deliberate. The first is to use `tessellatedfaces` JSON rather than glTF as the primary geometry format. Onshape documents no guarantee that glTF node names carry part IDs or instance hierarchy ([Translation guide](https://onshape-public.github.io/docs/api-adv/translation/)), while the tessellation JSON is keyed by partId. Mesh exports also create "a unique sub-mesh for each face", which the client should merge per part and per colour ([Onshape forum](https://forum.onshape.com/discussion/23958/exporting-parts-as-single-meshes-instead-of-many-sub-meshes)). The second is to **avoid the asynchronous assembly glTF export** entirely. It costs a POST, polling and a download, it records a translation in the team's document, and it would write a blob into their document if `storeInDocument` were left true ([Translation guide](https://onshape-public.github.io/docs/api-adv/translation/)).

The mate data needs care in four places. **Limits are absent from the definition** and must be joined from `/features` by mate name, with expression strings and units evaluated and per-configuration values resolved. Onshape has **four relation types** (gear, rack and pinion, screw, linear), and all four map onto the repo's `couple:{to, ratio}` convention ([Onshape Help: Relations](https://cad.onshape.com/help/Content/Assembly/relations.htm)). onshape-to-robot reads only gear ratios, so it misses the rack-and-pinion and linear relations that FTC cascade slides use. The definition-side field names for relations are not documented, which is why `src/mates.js` tries several names; the `/features` `BTMMateRelation` shape is the one to trust. Finally, `matevalues` gives the joint value the CAD was drawn at. That fills the joint spec's `restPos`/`q0` without asking the team, and it also covers parts that have no material: the Part Studio mass response reports `massMissingCount`, so the importer can flag zero-mass parts and fall back to a volume-times-aluminium estimate.

## CORS and a 2,500-call quota rule out OAuth as the main route

A static Cloudflare Pages app cannot call Onshape directly with any credential. Onshape staff state the API does not support CORS ([forum](https://forum.onshape.com/discussion/comment/42174); [forum](https://forum.onshape.com/discussion/comment/107304)). A direct probe on 2026-10-02 confirmed that neither `cad.onshape.com/api` nor `oauth.onshape.com/oauth/token` returns `Access-Control-Allow-Origin` to a `*.pages.dev` origin. Onshape's OAuth documentation describes the authorization-code flow with a client secret, 60-minute access tokens and long-lived refresh tokens. **It does not mention PKCE, and the server publishes no discovery document** ([Onshape OAuth](https://onshape-public.github.io/docs/auth/oauth/)). Any OAuth design therefore needs a Cloudflare Worker that holds the secret and relays calls.

The quota decides the rest. Since October 2025, Free, EDU Student and Standard plans get **2,500 API calls per user per year**, Professional gets 5,000 and Enterprise 10,000. Going over returns HTTP 402 for the rest of the year. Only API-key calls, private OAuth apps (counted "toward the app owner's limits, not end users'") and authenticated API Explorer calls count. **Public App Store OAuth apps and browser client calls are exempt** ([Onshape API Limits](https://onshape-public.github.io/docs/auth/limits/); [forum](https://forum.onshape.com/discussion/27916/api-limits)). A private OAuth app would charge every FTC team's imports to SimBench's own 2,500 calls: at an estimated 100–200 calls per robot, that is about 15 imports a year for the whole user base. API-key scripts like `tools/onshape-mates.mjs` spend the team's own budget, so they allow about a dozen imports a year. Making public documents anonymous doesn't help either. A probe of onshape-to-robot's public example document ([examples](https://github.com/Rhoban/onshape-to-robot-examples)) returned 401 for the assembly definition, features, tessellation and mass endpoints without credentials. "Paste a public link" still needs auth.

| Route | CORS | Quota | Backend | Verdict |
| --- | --- | --- | --- | --- |
| Bookmarklet on the team's Onshape tab (same-origin `fetch`, session cookie) | Not needed | Likely counted as a browser client call (unconfirmed) | None | **Primary, now** |
| Public App Store OAuth app + Worker relay | Worker adds headers for the app origin only | Exempt | Small Worker | **Second phase**, once Onshape approves the listing |
| Private OAuth app + Worker | Worker | App owner's 2,500/yr | Worker | Reject |
| User-pasted API keys | Worker or none | Team's 2,500/yr | Optional | Reject (teaches students to paste secrets) |

Three changes make the bookmarklet ready for full geometry. First, **all fetcher code stays inline in the `javascript:` URL**. The Onshape page's CSP limits `script-src-elem` to an allowlist that excludes `*.pages.dev`, but it has no `connect-src`, so same-origin `fetch('/api/...', {credentials:'include'})` works. The current file already follows this rule. Second, **replace the `#onshape=` fragment hand-off with `postMessage`** for anything over the current 1.5 MB fragment cap, because tessellation won't fit in a URL. The bookmarklet already opens the SimBench window during the click. SimBench posts `{ready, cachedKeys}` to `window.opener` with the Onshape origin pinned. The bookmarklet then skips Part Studios the app already holds in IndexedDB and transfers the rest as ArrayBuffers to the pinned SimBench origin. The app must check `event.origin` against `*.onshape.com`, as `checkOnshapePayload` already does for the URL. Third, **cache by immutable key**. Vendor parts fetched at `v/{versionId}` never change. Team Part Studios are keyed by microversion and revalidated when the new definition's `documentMicroversion` changes. Two risks are still open: Onshape doesn't say how it classifies cookie-authenticated `/api` calls made by user script, and its API terms on this kind of use weren't found in public text. The App Store listing is the hedge against both.

## Everyone else arrives through a SimBench exporter or a URDF zip

Joints never travel in the neutral formats students already export. STEP AP242 Edition 2 can carry ISO 10303-105 kinematics ([ISO](https://committee.iso.org/standard/78589.html)), but even Dassault describes kinematic export as something it "hopes to standardize" ([CADinterop](https://www.cadinterop.com/en/step.html)). None of Fusion, SolidWorks, Onshape, Inventor or FreeCAD is known to write it. A cheap scan for `*_PAIR` entities in the existing STEP parser costs little, but nothing should depend on it. glTF's `KHR_physics_rigid_bodies`, which includes joints, is still a **Review Draft** ([Khronos registry](https://github.com/KhronosGroup/glTF/blob/main/extensions/README.md)). `OMI_physics_joint` is a Stage 1 proposal implemented only in Godot ([OMI](https://github.com/omigroup/gltf-extensions/tree/main/extensions/2.0/OMI_physics_joint)), and no CAD tool writes either one. Browser USD runtimes such as Needle's OpenUSD WASM render geometry, but none was found that exposes UsdPhysics joints ([Needle](https://engine.needle.tools/docs/cloud/openusd.md)). SDF supports closed loops but has no JavaScript loader.

**URDF is the pragmatic interchange format.** Fusion (fusion2urdf forks, ACDC4Robot, Adriaeik/fusion2URDF), SolidWorks (sw_urdf_exporter), FreeCAD (CROSS) and Onshape (onshape-to-robot) all write it, and gkjohnson's Apache-2.0 `urdf-loaders` gives three.js a mature parser ([urdf-loaders](https://github.com/gkjohnson/urdf-loaders)). It carries joint type, origin, axis, limits, parent and child, mass, inertia and `mimic` couplings. It cannot express closed loops, so a slider-crank or four-bar needs SimBench's `couple.via` linkages on top. MJCF expresses more (equality constraints, actuators), and DeepMind now ships official WASM bindings as `@mujoco/mujoco`, whose single-threaded build needs no special headers on static hosting ([MuJoCo JS README](https://cdn.jsdelivr.net/npm/@mujoco/mujoco@3.9.0/README.md)). That makes MJCF a physics-engine option for later rather than an import priority, since only ACDC4Robot writes it from CAD.

Per tool, the routes differ in how much work the student does:

| CAD tool | Zero-install today | What to build | Joints carried |
| --- | --- | --- | --- |
| Onshape | Bookmarklet (above) | Extend it with geometry, mass and matevalues | Yes, all mate types and relations |
| Fusion | ACDC4Robot from the App Store → URDF, but only for a flat component tree, which FTC robots rarely have ([ACDC4Robot](https://github.com/bionicdl-sustech/ACDC4Robot)) | **"Export to SimBench" Python script** | Yes: `JointLimits` in cm or rad ([Autodesk API](https://help.autodesk.com/cloudhelp/ENU/Fusion-360-API/files/JointLimits.htm)) |
| SolidWorks | Save As GLB keeps appearances, configurations and metadata, but not joints ([SolidWorks Help](https://help.solidworks.com/2025/English/SolidWorks/sldworks/t_export_using_extended_reality.htm)); sw_urdf_exporter needs the link tree built by hand ([ROS wiki](https://mirror.umd.edu/roswiki/sw_urdf_exporter.html)) | `.swp` macro that reads mates and writes the same JSON | Through the macro or URDF |
| FreeCAD | CROSS → URDF ([CROSS](https://github.com/galou/freecad.cross)) | Nothing new; reuse the URDF importer | Yes, through CROSS |
| Inventor, others | STEP + SimBench joint editor | Nothing until demand shows up | Through the editor |

The Fusion script should be a **script, not an add-in**. Students install it with Utilities → Scripts and Add-Ins → "+" → Run, with no App Store review. It walks `rootComponent.allOccurrences` for names, appearance colours and physical properties, and walks `allJoints` plus `allAsBuiltJoints` for type, both occurrences, origin, axis and limits (converting cm to m). It treats rigid groups as single bodies and writes the package JSON next to OBJ or 3MF meshes. Fusion has **no native glTF export**, only 3MF, OBJ, FBX, STEP, STL and USDZ ([Fusion formats](https://help.autodesk.com/cloudhelp/ENU/Fusion-Designs/files/TPD-SUPPORTED-FILE-FORMATS.htm)). Adriaeik/fusion2URDF shows that nested assemblies five levels deep and merged rigid groups are achievable ([fusion2URDF](https://github.com/Adriaeik/fusion2URDF)). Two Fusion API details could not be confirmed because the reference pages returned 404: the exact `Joint` property names, and how Fusion's Motion Links (its coupled joints) are exposed. Check both against the live API before coding.

## One package binds device names to joints by exact string

Every mature simulator splits geometry and kinematics, actuation, and the name code uses to reach a device, and **binds that name by exact string with no guessing**. In Webots, `getDevice("lift")` returns the first device whose `name` field matches, and a motor drives the joint whose `device` slot holds it. Motors named `lift::left` and `lift::right` are logically coupled, each with its own `multiplier` ([Webots Robot](https://cyberbotics.com/doc/reference/robot#wb_robot_get_device); [Webots Motor](https://cyberbotics.com/doc/reference/motor)). In ros2_control the URDF joint name, the `<ros2_control><joint>` entry and the controller YAML all share one string. A `SimpleTransmission` maps actuator to joint with `mechanical_reduction`, `offset`, and a sign that encodes direction ([ros2_control types](https://control.ros.org/master/doc/ros2_control/hardware_interface/doc/hardware_interface_types_userdoc.html); [simple_transmission.hpp](https://github.com/ros-controls/ros2_control/blob/master/transmission_interface/include/transmission_interface/simple_transmission.hpp)). MuJoCo binds `<actuator joint="…" gear="…">` and couples joints with a quartic `equality/joint` polynomial ([MuJoCo XML](https://mujoco.readthedocs.io/en/stable/XMLreference.html#equality-joint)).

FTC tools take the opposite approach. virtual_robot hard-codes names such as `back_left_motor` and `arm_motor` in each bot class, so teams must rename their devices to match the sim ([MecanumPhysicsBase.java](https://github.com/Beta8397/virtual_robot/blob/master/Controller/src/virtual_robot/robots/classes/MecanumPhysicsBase.java)). MeepMeep models only drive constraints and a box ([MeepMeep](https://github.com/acmerobotics/MeepMeep)). AdvantageScope has no joints at all. Teams split their CAD into `model_N.glb` files, and the code logs one pose per component ([AdvantageScope](https://docs.advantagescope.org/more-features/custom-assets)). WPILib describes each mechanism as a handful of numbers in code (gearing, mass, drum radius, limits, gravity), and CAD has no role in its dynamics ([WPILib physics sim](https://github.com/wpilibsuite/frc-docs/blob/main/source/docs/software/wpilib-tools/robot-simulation/physics-sim.rst)). SimBench's premise of running unmodified code reverses the FTC habit: **the package owns a name-to-joint table, and the team's own names are the keys.**

The package should be a superset of today's `ftc-sim-bench.joints` and should land through the same `cad.mates` path, so `mateJointQ`, `jointValues` and `classifyMechs` work unchanged. Meshes are deduplicated as the Onshape fetch is, by storing unique meshes once and placing occurrences by transform. Lengths are in metres and angles in radians, matching URDF, Onshape and `src/mates.js`. The hand-written joints spec keeps millimetres and degrees as an authoring convenience.

```jsonc

  "units": { "length": "m", "angle": "rad" },
  "frame": { "up": "+z", "origin": "drivetrain centre on floor", "front": "+x" },   // src/frame.js
  "source": { "exporter": "onshape-bookmarklet|fusion-script|sw-macro|urdf|hand",
              "cad": { "url": "...", "microversion": "..." } },
  "meshes": { "m_gb_channel_288": { "file": "meshes/m_gb_channel_288.glb", "partNumber": "1120-0001-0288" } },

  "links": [ { "id": "base" }, { "id": "lift1" } ],
```

The binding lives on the actuator and is **one joint to many devices**, because FTC lifts are often driven by paired motors (`uppies`/`uppies1` in the default robot). `sign` follows the repo's motor convention: FORWARD means clockwise seen from the shaft end, and ticks count up under positive commanded power. virtual_robot's `MotorType` uses the same reference for `REVERSED` and provides a ready catalog of ticks per revolution, gearing and torque ([MotorType.java](https://github.com/Beta8397/virtual_robot/blob/master/Controller/src/com/qualcomm/robotcore/hardware/configuration/MotorType.java)). Couplings stay separate from actuators, because a mimic joint "must not have command interfaces" ([gz_ros2_control](https://control.ros.org/master/doc/gz_ros2_control/doc/index.html)).

Matching runs once, when the package is written, and its output is always exact strings. Five rules apply in order, each narrowing the candidates for the next. The first is **the Control Hub configuration XML**, the team-authored, case-sensitive list of which names exist, plus each device's type and motor family ([FTC Docs](https://ftc-docs.firstinspires.org/hardware_and_software_configuration/configuring/configuring_dc_motor/configuring-dc-motor.html); [REV Docs](https://docs.revrobotics.com/duo-control/hello-robot-java/configuration)). The repo already parses it in `src/robotconfig.js`, and with it a positional servo never lands on a continuous joint and a motor never lands on a fastened one. The second is **device names found in mate names**: any word in a mate's name that equals a configured device name binds that device to the joint, so a mate called "Lift (uppies, uppies1)" binds both motors with no special syntax. onshape-to-robot's `dof_<name>` form and its axis-flipping `_inv` suffix are accepted as well ([onshape-to-robot design](https://onshape-to-robot.readthedocs.io/en/stable/_sources/design.rst.txt)), and default names such as "Revolute 3" are skipped with the regex already in `src/mates.js`. The third is **normalised name and synonym matching** of mate, part and subassembly names after splitting camelCase, with an FTC synonym table (lift/slide/viper/elevator/uppies, arm/pivot, claw/grip/pinch, and the front-left drive-motor variants). The fourth is **geometric evidence**: a motor or servo part number whose shaft is collinear with a revolute axis, or sits next to a slide's spool, counts toward that joint. The fifth is **code-usage evidence** from the team's OpModes; `setTargetPosition(2650)` on a slide-like name, for example, points to a prismatic joint. No published FTC name-matching dataset exists, so the synonym table should grow from the names teams actually confirm.

Only rules 1 and 2, or a score above a high threshold, apply automatically. Everything else appears as a one-click suggestion, and accepting it writes `confirmed: true`, so the question comes up once per robot and never again. A device with no joint still gets a full simulated device and appears as a live gauge. That is what ros2_control's mock hardware and virtual_robot do: code is never refused a device because the CAD lacks a joint ([ros2_control mock components](https://control.ros.org/master/doc/ros2_control/hardware_interface/doc/mock_components_userdoc.html)).

## Run unmodified Java with a generator-based interpreter, not a JVM

Teams keep hardware in Robot and subsystem classes, drive through Road Runner or Pedro, and schedule FTCLib commands. All of that means following calls into objects defined in other files, which a statement-level regex reader such as `src/java.js` cannot do. The choice is between a real JVM in the browser and a Java-subset interpreter, and **the interpreter wins for a simulator whose job is to explain the robot**.

On the JVM side, Doppio is abandoned (last commit 2021) ([Doppio](https://github.com/plasma-umass/doppio)), GraalVM Web Image is an experimental build-time tool ([GraalVM](https://www.graalvm.org/dev/reference-manual/web-image/)), and Janino cannot compile lambdas and ignores generics, which rules out FTCLib code ([Janino](https://janino-compiler.github.io/janino/)). That leaves two serious options. **CheerpJ 4.3** is a full OpenJDK JVM with an interpreter and JIT, and JavaFiddle runs stock `javac` on it from an **18.3 MB `tools.jar`** ([CheerpJ architecture](https://cheerpj.com/docs/explanation/architecture); [JavaFiddle](https://github.com/leaningtech/javafiddle)). Its free licence, however, covers only individuals and FOSS projects loading the runtime from Leaning Tech's CDN. Self-hosting and multi-person organisations need a commercial licence, and education gets a "special quote" ([CheerpJ licensing](https://cheerpj.com/docs/licensing)). Java code under CheerpJ also reads wall-clock time through `System.nanoTime`, which Road Runner's actions use, and every JS-to-Java call is async. That makes deterministic, faster-than-real-time 20 ms stepping hard. **teavm-javac** packs OpenJDK javac and the TeaVM compiler into one Apache-2.0 WASM module of about **1.57 MB gzipped** (about 4.1 MB on the wire with its class libraries). It uses CPS coroutines for threads, so a custom class library could swap in a virtual clock ([teavm-javac](https://github.com/konsoletyper/teavm-javac); [TeaVM coroutines](https://www.teavm.org/docs/runtime/coroutines.html)). Nobody has measured its in-browser compile-plus-WASM-generation time on a 20–40 file TeamCode with Road Runner's Kotlin jar, and its class library's coverage of the Kotlin stdlib is unverified.

The interpreter path is cheap where it counts. `java-parser` 3.0.1 (Apache-2.0) bundles to **65 KB gzipped**, and in local tests it parsed all 1,642 lines of the repo's team code, including Road Runner's `MecanumDrive.java`, with zero errors in 41 ms warm ([java-parser](https://www.npmjs.com/package/java-parser)). A generator-based evaluator turns blocking `LinearOpMode` code into resumable steps. The sim calls `next()` once per 20 ms tick, and `sleep(1000)` simply spans 50 ticks of virtual time. `ElapsedTime`, `System.nanoTime` and Road Runner's clock all read the sim clock, so runs are deterministic and replayable, and per-node source positions show which line set which motor and which lines never ran. The repo already has this design in an uncommitted `src/jvm.js` (1,648 lines). It has its own lexer and parser, classes, inheritance, inner and anonymous classes, enums, lambdas, collections, exceptions and switch, and it uses generator gates at `opModeIsActive()`, `idle()` and `sleep()`. Its header names a `src/jvmlib.js` for the SDK and libraries, which does not exist in the tree yet. That file is the next piece of work, and it should be built in this order:

| Layer | Strategy | Why |
| --- | --- | --- |
| Team code, including their `MecanumDrive.java` (RR 1.0), `SampleMecanumDrive.java` (RR 0.5) and Pedro `Constants.java` | Interpret as written | Catches the team's real motor names, directions and `PARAMS`; a mock would silently fix their bugs |
| FTC SDK | JS mocks following VirtualRobot's checklist of about 75 `com.qualcomm` and 40 `org.firstinspires` classes ([virtual_robot](https://github.com/Beta8397/virtual_robot)) | Include `HardwareMap.get/getAll/tryGet` and the legacy `hardwareMap.dcMotor.get`, `RunMode`s, `LynxModule` bulk caching, `IMU`, `GoBildaPinpointDriver`, `SparkFunOTOS`, `Telemetry`/`MultipleTelemetry`, and gamepad edges from SDK 10.3, trigger edges from 11.1, and SDK 12.0 changes ([FtcRobotController](https://github.com/FIRST-Tech-Challenge/FtcRobotController)) |
| FTCLib, Pedro Pathing 2.x | **Interpret their real Java source**, shipped as static assets (BSD-style and BSD-3) ([FTCLib](https://github.com/FTCLib/FTCLib); [Pedro](https://github.com/Pedro-Pathing/PedroPathing)) | `CommandScheduler`, `GamepadEx`, `Follower` behave exactly as on the robot, and API changes (Pedro 1.x `setTeleOpMovementVectors` became 2.x `setTeleOpDrive`) are absorbed by updating the source |
| Road Runner 1.0 / 0.5 core | JS port, extending `src/roadrunner.js` | The core is Kotlin (30 `.kt` files), which a Java interpreter cannot run ([road-runner](https://github.com/acmerobotics/road-runner)) |

The interpreter should yield at `sleep`, `idle`, `waitForStart`, `opModeIsActive`/`isStopRequested`/`opModeInInit`, each `Actions.runBlocking` step and `CommandScheduler.run`. It also needs a loop back-edge budget, so that a busy-wait is reported with its line number instead of hanging the tab. The interpreter's main risk is semantic drift: overload resolution, `int`/`long`/`char` arithmetic, static initialisation order and inner-class capture. To control it, add a conformance corpus that CI runs both through the interpreter and on a real JDK, diffing telemetry and motor-power traces. Anything unsupported should be reported as "line N: unsupported X" and never skipped silently. Keep teavm-javac as an optional **"would this compile?" check** against a stub SDK jar, which gives real javac diagnostics at little cost, and as a spike for a future exact-JVM mode. Use CheerpJ only if the project commits to staying a one-person or FOSS effort. No other browser FTC sim runs arbitrary multi-file team code: FTCSim's Java execution is undocumented ([FTCSim](https://ftcsim.org)), and VRS only *planned* GraalVM javac plus CheerpJ in May 2025 ([Chief Delphi VRS](https://www.chiefdelphi.com/t/join-the-virtual-robot-simulator-vrs-development-team/501946)).

## Conclusion

The question has shifted from inferring mechanisms to reading joints the team already declared. Onshape mates, Fusion joints and the Control Hub configuration together hold almost every fact the sim needs, and the remaining unknowns, mostly which motor drives which mate, are best settled once per robot as exact strings that the team can see and share. Two external constraints shape the architecture more than any technical preference. Onshape's quota policy turns the bookmarklet from a hack into the scalable route, at least until an App Store listing exists. CheerpJ's licence turns the interpreter from a compromise into the safer long-term bet. The open questions are empirical and cheap to settle with three spikes: the real call count and payload size of a full FTC assembly import, how Onshape classifies session-cookie API calls, and teavm-javac's compile time on a real TeamCode. Run those before committing to steps 2 and 7.
