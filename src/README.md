# src/ — the app

Every file here is a **plain script fragment**: no `import`, no `export`, no bundler.
`tools/build.mjs` concatenates them in its `ORDER` into one `"use strict"` scope inside
`dist/index.html`, so a later file can use what an earlier one declares.

The split that matters:

- **Engine:** every file except the four marked 🖥. It never touches the DOM or three.js.
  `tests/load.mjs` evaluates it in Node exactly as it ships, so the parser, physics and sim are
  tested without a browser.
- **Browser side** (🖥): `tessellate.js`, `view3d.js`, `cadview.js`, `engineworker.js`, `importflow.js`, `app.js`.

Files are listed in build order. The number in each file's header comment is the order the bench
was designed in, not the build order.

## CAD → a robot

| File | What it does |
|---|---|
| `hardware.js` | The actuator database: goBILDA / REV motors and servos by part number (ratio, rpm, stall torque, servo range), and the spec a device ends up with. |
| `samples.js` | The built-in sample robot and sample OpModes (`?robot=sample`). |
| `step.js` | STEP (AP203/214/242) parser: records, the assembly tree, placements, one solid per part, part kinds, the occurrence list, and the old nearest-mechanism guess (`classifyMechs`). Canonicalises the frame once parsing is done. |
| `hull.js` | Convex hulls, so every part is a solid. |
| `inertia.js` | Mass, centre of mass and inertia from part shapes, materials and vendor figures. |
| `frame.js` | The robot frame: +z up, origin at the drivetrain centre on the floor. `robotToWorld` is the one placement contract for physics, collisions and the view. |
| `drivetrain.js` | Wheels, drivetrain type (mecanum, tank, swerve, kiwi, X), each motor's mounting sign, and the inverse and forward kinematics. |

## Joints

| File | What it does |
|---|---|
| `meshfiles.js` | A robot export's zip and the meshes in it, all on the page: the zip reader (stored and deflate), glTF/GLB (positions, indices, node transforms, material colours; Draco refused with the fix), OBJ with its MTL. |
| `urdf.js` | URDF → the same robot an Onshape import gives: links are parts, joints are mates, `mimic` a coupling. `urdfFromZip` reads Onshape's URDF export (the main way in); `urdfCoupleHints` infers what URDF can't carry (a cascade's stages, a mirrored gear pair) as hints. |
| `mates.js` | An Onshape assembly definition → exact joints: parts fastened together, grouped or sharing a still sub-assembly collapse into rigid links; the moving mates are walked out from the chassis as the joint tree, each with its true axis, pivot, limits and gear/rack/screw relations. The URDF route writes the same document (`src/urdf.js`), so both routes land here. |
| `net.js` | Online matches: the lobby, rooms and places, one clock, each player's robot to everyone, the host's match to the guests, shots decided by the host, chat and marks. Every message from another computer is checked. The transport is handed in (Trystero in the browser, an in-process one in the tests). See [../docs/online.md](../docs/online.md). |
| `netrelay.js` | The transport ladder: `netRelay`, the site's own match rooms (`functions/room`, `workers/room`) as a transport, over a WebSocket or Server-Sent Events + POST, with the room's clock; `netConnect` picks the rooms, else WebRTC through TURN, else plain WebRTC. See [../docs/online.md](../docs/online.md). |
| `onshapelink.js` | The pasted Onshape link: `onshapeRef` reads the address (configuration included), `onshapeRead` fetches the assembly definition, its features and, once per Part Studio, each part's tessellated faces and mass properties through the **Sign in with Onshape** relay (`functions/onshape`); `onshapeFromLink` is the page's call, and runs in the engine worker too. `checkOnshapePayload` treats what arrives as untrusted. |
| `onshapecad.js` | The robot from that read: one thinned shape per unique part (drawn as instances, like the URDF route), one solid per occurrence with its placement and Onshape's mass, centre and inertia tensor, the frame, the mates as joints, and `onshapeLinks`: each rigid link's exact mass properties summed from its parts, and what each joint carries. |
| `autorig-lib.js` | Generated by `tools/gen-autorig.mjs` from `research/autorig`: the actuator, slide and contact-graph finders, exactly as measured. Don't edit it by hand. |
| `autorig.js` | The automatic joint finder: slides, actuators and gear followers into joints; the contact graph cut into rigid bodies; owners and parents; a joint spec with a list of what to check. |
| `match.js` | The rest of the match: three AI robots and both alliances' human players, by the manual's rules, sharing the field and the HIVEs with the team's robot; path planning, contact, scoring. See [../docs/match.md](../docs/match.md). |
| `bind.js` | Which joints are mechanisms at all (`classifyJoints`: the library's bearing races and motor shafts come through as joints and are marked internal), and which device drives each (`bindDevices`: names, the actuator kind on the axis, the code's travel, elimination; a coupling hint becomes a coupling when the code drives its leader). What is left is a question with its candidates. |
| `robotcheck.js` | The robot check: the joints against the team's OpMode (devices, joints, drivetrain, a small swing of each joint against the frame), as questions with likely answers. See [../docs/robot-check.md](../docs/robot-check.md). |
| `jointspec.js` | Joint specs (`ftc-sim-bench.joints`). Part picks by path, name and position; axis, pivot, travel, devices, rest poses; followers (ratio, slider-crank, rod); hand fixes. Also the joint editor's helpers: `specFromCad`, `suggestJoint`, and `mateJointQ`/`jointValues`, which the sim and the view share. See [../docs/joints.md](../docs/joints.md). |

## Code → behaviour

| File | What it does |
|---|---|
| `expr.js` | The expression language: arithmetic, comparisons, gamepad reads, device reads, PID calls, the team's static helper methods. |
| `java.js` | The OpMode parser: devices and their config names, fields, INIT, the main loop, autonomous sequences, `if`/`for`/`switch`/enums, FTCLib detection. |
| `roadrunner.js` | Road Runner 1.0: helper classes (Action inner classes, factories, static PID helpers, `MecanumDrive` `PARAMS`), builder chains → quintic/line paths with time profiles, the action tree runtime, the follower. See [../docs/code-support.md](../docs/code-support.md). |
| `mapping.js` | Which code device drives which joint (`autoMap`): names, config names, the CAD actuator. |
| `robotconfig.js` | Reads the Robot Controller's `.xml` config and checks every `hardwareMap` name against it. |
| `compare.js` | Diffs two OpModes. |
| `analyze.js` | The Checks tab: mapping, stalls, sleeps, travel, joints nothing drives, a Road Runner plan summary. |

## The world

| File | What it does |
|---|---|
| `dynamics.js` | The chassis as a rigid body on N contact patches: motor torque curves, load transfer, slip-limited friction. |
| `joltmech.js` | Solved mechanisms (Physics → Mechanisms → solved): the robot's joints in Jolt Physics (loaded on demand): CAD masses under gravity, motor curves as torque caps, reflected rotor inertia, limits, gear and rack constraints, followers, loops pinned closed. Posed (the default) needs none of it. |
| `field.js` | The BIOBUZZ field: walls, HIVEs, FLOWERs, zones, start poses, collisions. |
| `shots.js` | The running OpMode's shooter on the field, through the vendored shot engine. |
| `controllers.js` | Real gamepads, read the way the FTC SDK reads them. |
| `sim.js` | The Driver Station: INIT / START / STOP, 50 Hz ticks, devices, motors, servos, PIDs, the loop and auto steppers, the Road Runner runtime, sensors, the drive probe. |

## Product layer

| File | What it does |
|---|---|
| `session.js` | `.ftcsim` workspaces: the parsed robot, joints, code, map and pose in one JSON, validated as untrusted input. |
| `mathdoc.js` | The Math tab and its Markdown export. |
| `gitimport.js` | Import OpModes from a public GitHub repo. |

## Browser side 🖥

| File | What it does |
|---|---|
| `tessellate.js` | Exact geometry: one mini STEP per unique shape, meshed by OpenCascade (occt-import-js) in up to four Web Workers, then placed at every occurrence and matched to the parser's solids. |
| `view3d.js` | The three.js (r186) scene with GTAO ambient occlusion, SMAA and a studio environment: the field, the robot, instanced exact meshes, materials, the joint hierarchy posed each frame from the sim (`mechPose`, `jointValues`), spinning wheels. |
| `cadview.js` | The Onshape-style CAD view and the click-to-fix joint editor. |
| `engineworker.js` | The engine (`dist/engine-<hash>.js`) in a Web Worker: a STEP is parsed, its joints found and its shapes cut off the page's thread; a URDF zip is unpacked and built there too. Falls back to the page when a worker can't start. |
| `importflow.js` | The import card: bring the robot, add the code, review what was found and answer the little that's left. Draws `bind.js` and `robotcheck.js`; decides nothing itself. |
| `app.js` | The UI: panels, the OpMode library and helper classes, file intake, the default robot loader, mates and joint specs, the joint editor's actions, sessions. |
| `markup.html`, `styles.css` | The page. |

Conventions both coding agents rely on (motor direction, the robot frame, joint kinds, joint
specs) are in [../AGENTS.md](../AGENTS.md).
